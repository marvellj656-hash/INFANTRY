# 裁判系统 UI：九个旧元素的 FreeRTOS 移植

本模块保留旧屏幕布局和配色，任务只从 `cmd_get_state()` / `referee_get_state()` 读副本。它不读取 `debug_*` 充当消息，也不自行开启 USART6。

| 元素 | 屏幕坐标 / 外观 | 含义 |
|---|---|---|
| Frc | (430,850)，35号字 | 摩擦轮指令开启为绿，关闭/指令过期为紫红 |
| Rot | (430,775)，35号字 | 小陀螺指令为绿，其余为紫红 |
| Aim | (430,700)，35号字 | 有效自瞄控制指令为绿，其余为紫红 |
| Heat | (1320,720)，35号字 | `Heat:当前热量/热量上限`；数据过期显示 `Heat:---/---` |
| 水平准星 | (935,540) → (985,540)，青色 | 保留旧准星 |
| 垂直准星 | (960,570) → (960,180)，青色 | 保留旧长竖线 |
| 瞄准圈 | 圆心(960,540)，半径250 | 队伍色 |
| 左车宽线 | (529,102) → (783,445)，橙色 | 车宽参考 |
| 右车宽线 | (1391,102) → (1137,445)，橙色 | 车宽参考 |

三个状态灯沿用旧版**指令状态**语义：Frc变绿说明要求开摩擦轮，不代表已达到目标转速；需要看是否真正转起来，读取 shoot/motor 快照和相应调试变量。

`Modules/referee_ui` 是纯字节编码和九元素轮转；`Task/referee_ui` 每100ms提交一个元素。一圈900ms，既可持续更新，也不会用旧通用优先级队列把逻辑铺得很大。

图形名字固定为 `HN0`..`HN8`。第一次用 ADD，之后用同名 MODIFY；上电、身份变化、裁判链路恢复和 R 键刷新会重新 ADD。裁判快照的 `generation` 能记住短暂重连，UI不会因为100ms才运行一次而错过2ms内完成的断线恢复。R 由 cmd 的10ms任务调用 `referee_ui_request_redraw()`，请求用计数锁存，所以100ms UI任务不会漏掉短按。

图形数据不是 C 位域结构体：三个名字字节后面是三个明确的小端32位字，按旧协议逐位放入。

| 32位字 | 各字段，从低位到高位 |
|---|---|
| 第1个 | 操作3位、图形类型3位、图层4位、颜色4位、字号/起始角9位、字符数/终止角9位 |
| 第2个 | 线宽10位、起点X 11位、起点Y 11位 |
| 第3个 | 半径10位、终点X 11位、终点Y 11位 |

单图形正文15字节，内层命令 `0x0101`；文字正文45字节（15字节图形+30字节字符），内层命令 `0x0110`。外层 `0x0301`、sender、seq、CRC8/CRC16 都由 `referee_send_interaction()` 管理。UI只提交内层正文，不再重复造UART/DMA或CRC代码。

客户端 ID 使用 `0x0100 + robot_id`，例如红3为 `0x0103`、蓝3为 `0x0167`。只为有操作手客户端的红1..6、蓝101..106发送；未收到新鲜身份不会硬编码红3。所有坐标保留旧1920×1080布局，换屏幕布局应在模块里改配置值。

发送队列拒绝一包时不推进轮转，下一次继续尝试原元素。`debug_referee_ui.queued` 仅表示交给发送队列，并不是客户端确认显示；真正交给UART可看 `debug_referee.tx_accepted`。协议没有对单图形的客户端确认，漏图时按 R 重画。

验证：客户端先看到9个元素；切摩擦轮/小陀螺/自瞄，相应文字在一圈约900ms内改色；停止热量报文，应显示 `---`；R重新画九个元素；拔插裁判串口恢复后也应重新 ADD。

`Tests/test_referee_ui.c` 检查9个布局、图形字段的位位置、client ID、首轮ADD/后续MODIFY、busy重试不前进、指令过期回紫色、热量过期及65535边界文本。编译和主机测试不能替代裁判客户端实际渲染验证。
